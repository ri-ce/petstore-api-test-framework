# 项目面试讲解卡

## 30 秒介绍

这是我独立完成的接口自动化测试项目，被测对象是一个校园二手交易平台的本地演示 API。
我使用 Pytest 和 Requests 搭建了分层框架，把 HTTP 会话、业务接口和测试数据分开，
并通过 fixture 自动启动服务、重置数据和完成登录。项目设计了 53 条用例，覆盖登录鉴权、
商品增删改查、权限控制、下单和库存一致性，当前全部通过，并接入了 GitHub Actions。

## 2 分钟讲解

我先梳理了登录、发布商品、浏览筛选、下单和取消订单这几条核心链路，然后按功能、
异常、边界和权限四个方向设计测试点。

框架分为三层：测试用例负责业务场景和断言，Service 层封装登录、商品和订单接口，
底层使用 Requests Session 统一维护地址、超时和 Token。`conftest.py` 负责启动随机端口
的演示服务，并在每个用例前重置数据，避免测试互相污染。参数化用于覆盖非法价格、库存
和购买数量等边界场景。

项目里我比较关注状态一致性。例如下单后不仅检查订单状态，还会再次查询商品库存；
取消订单后会检查库存是否恢复；重复取消则检查返回 409。这样测试不只验证响应码，
还验证业务状态是否真的正确。

项目接入 GitHub Actions 后，每次提交都会自动启动一份全新环境并执行完整回归，
HTML 报告作为构建产物保存。

## 高频追问

### 为什么使用 fixture 重置数据？

接口测试会产生订单、库存变化等副作用。如果不隔离，前一个用例的数据可能让后一个用例
成功或失败，导致结果不可重复。我在每个用例前恢复种子数据，业务数据再由 fixture 实时
创建，保证用例独立。

### 为什么不是只断言状态码？

状态码只能说明请求被接受或拒绝，不能证明业务结果正确。例如下单接口返回 201，但库存
可能没有扣减，或者订单金额计算错误。因此断言还包含响应字段、订单归属、库存变化和
后续查询结果。

### 参数化解决了什么问题？

库存、价格和购买数量这类场景的数据结构相同，只有输入值和预期结果不同。参数化避免
复制多份测试函数，也让失败报告直接显示是哪组数据出错。

### 如何继续改进？

- 接入 Allure，补充失败截图、请求响应和用例分级。
- 增加数据库校验，验证接口结果和持久层数据一致。
- 增加 Docker Compose，统一本地与 CI 环境。
- 增加并发下单测试，验证库存竞争和幂等性。
- 对核心流程接入性能测试，观察吞吐量和错误率。

### 项目里遇到的问题

最初测试用例通过管道接收被测服务的日志，长时间运行时子进程输出没有及时消费，
出现过测试服务异常导致后续用例连续失败。改为隔离服务日志输出后，完整回归稳定通过。
这个过程让我认识到：测试框架本身也需要可靠性和故障隔离。

## 不要这样说

- 不要说这是企业真实项目。
- 不要说自己做过性能、安全或大数据测试。
- 不要把测试用例数量等同于业务复杂度。
- 如果面试官追问某个工具，只讲真正运行过并理解的部分。
