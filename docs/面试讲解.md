# 项目面试讲解卡

## 30 秒介绍

这是我基于 Swagger 官方公开的 Petstore API 完成的接口自动化测试项目。被测系统是真实在线的
第三方开源服务，不是我编写的业务应用。我使用 Pytest 和 Requests 搭建分层框架，
通过 OpenAPI 文档做契约校验，并覆盖宠物 CRUD、状态查询、库存和订单生命周期。
项目包含 22 条自动化用例，全部通过，并接入 GitHub Actions。

## 2 分钟讲解

被测对象是 Swagger Petstore v3，一个由 Swagger 官方维护的公开 REST API。
我先读取 `/openapi.json`，确认宠物和订单接口的路径、HTTP 方法和响应结构，
然后按正常流程、状态变化和异常输入设计测试。

框架分为三层：测试用例负责业务场景和断言，服务层封装宠物、订单和系统接口，
底层使用 Requests Session 统一管理 URL、超时、日志和网络重试。
`conftest.py` 使用随机唯一 ID 创建宠物和订单，并在用例结束后自动删除，
避免公共环境的测试数据互相影响。

项目不仅验证状态码，还验证业务字段和状态变化。例如创建宠物后再次查询，
确认名称、分类和标签被真实保存；修改后再次查询，确认更新生效；删除后查询，
确认返回 404。这样测试的是业务结果，而不是只看接口有没有返回 200。

## 高频追问

### 被测系统为什么选择公开 API？

自己编写的业务系统和测试代码容易让人怀疑测试独立性。Swagger Petstore 是第三方公开系统，
有正式的 OpenAPI 文档，接口真实在线，因此可以展示我测试别人系统的能力。

### 公共 API 不稳定怎么办？

我对连接失败、超时和部分临时服务端错误设置了有限次数、指数退避重试。
但重试只处理网络和临时服务异常，如果业务断言失败，测试不会被重试掩盖。

### 如何避免测试数据互相影响？

创建资源时使用随机唯一 ID，不依赖固定种子数据；测试结束后由 fixture 自动删除。
资源 ID 和测试框架相互独立，即使公共环境中存在大量其他人的数据，也不会使用固定 ID 发生冲突。

### 为什么先做 OpenAPI 契约测试？

如果路径或方法被上游修改，业务测试会在运行前出现大量难以定位的失败。契约测试可以快速说明
被测服务是否仍符合测试框架依赖的接口定义。

### 项目中发现过什么问题？

最初按经验假设删除后查询会返回 JSON，但实际 Petstore V3 返回的是纯文本 `Pet not found`；
非法 ID 类型返回 `400`，不是 `404`。我根据真实接口行为修正了断言，这也体现了接口测试必须以
实际契约和响应为依据，不能只凭经验猜测。

### 如何继续改进？

- 使用本地 Docker 启动同一份开源 Petstore，增加可离线执行的测试任务。
- 接入 Allure，补充请求响应和失败附件。
- 增加 Schema 级响应校验和参数化数据生成。
- 增加并发测试，观察公共 API 的限流和超时行为。
- 补充性能测试，但不把学习结果描述成企业压测数据。

## 表述边界

- 可以说“测试 Swagger 官方公开 API”。
- 不要说“负责 Swagger Petstore 企业项目”。
- 不要说这是公司真实生产环境。
- 不要把第三方服务的功能归为自己开发。
