# 软件测试作品集面试讲解

## 一句话介绍

我准备了一个接口自动化测试项目和一个网页自动化测试项目，分别验证真实公开接口和真实商城网页，
一共 34 条测试用例，并通过 GitHub Actions 自动执行。

## 2 分钟项目介绍

第一个项目测试 Swagger 官方公开的 Petstore 接口。我使用 Pytest 和 Requests 搭建服务层，
以 OpenAPI 文档作为契约来源，覆盖宠物增删改查、状态查询、库存和订单生命周期。
测试使用随机唯一 ID，结束后自动删除数据，并加入网络超时和有限重试。

第二个项目使用 Playwright 自动控制真实浏览器测试 SauceDemo 商城。我采用页面对象模式，
把登录页、商品页、购物车和结算页的操作分别封装，覆盖登录、错误账号、商品排序、
加入和移除购物车、结算表单校验及完整下单流程。

两个项目都接入 GitHub Actions 和 HTML 测试报告。接口项目有 22 条用例，
网页项目有 12 条用例，最近一次执行全部通过。

## 项目互补关系

| 项目 | 证明的能力 |
| --- | --- |
| Petstore 接口测试 | 接口、状态码、字段、数据清理、OpenAPI |
| SauceDemo 网页测试 | 页面交互、元素定位、等待、页面对象、端到端流程 |

接口测试速度快，适合频繁回归；网页测试更接近真实用户操作，但执行成本更高。
两者结合可以覆盖同一产品的不同层面。

## 常见追问

### 你的用例是怎么设计的？

先从公开网站的接口文档和用户操作流程确认正常路径，再补充错误输入、权限或异常状态、
数据状态变化。接口项目重点检查响应字段和后续查询结果；网页项目重点检查页面显示、
提示信息和结算结果。

### 为什么网页测试使用页面对象？

如果登录框、购物车按钮的定位代码散落在所有用例里，页面变化后要修改很多地方。
页面对象把同一页面的元素和操作封装起来，测试用例只表达业务步骤，维护成本更低。

### 为什么不用固定等待几秒？

固定等待会让测试变慢，而且网络快时浪费时间、网络慢时仍然失败。Playwright 会等待元素
进入可操作状态，并设置超时，因此比固定等待稳定。

### 网页测试为什么每个用例重新登录？

每个用例使用独立浏览器上下文，避免购物车、Cookie 和登录状态互相污染。
这样单条用例可以独立运行，也更容易定位失败。

### 接口和网页测试的缺点是什么？

接口测试不验证页面布局和视觉问题；网页测试运行更慢，也更依赖页面结构稳定。
实际项目中通常以接口自动化覆盖核心回归，用少量关键网页流程做端到端测试。

### 如何继续改进？

- 将两个项目拆分目录并建立统一测试依赖管理。
- 增加 Allure 或 Playwright Trace 报告。
- 增加接口 Schema 自动校验。
- 增加移动端和跨浏览器测试。
- 增加失败重试策略和测试环境开关。
